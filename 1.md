# Engineering Operating Protocol

A protocol for landing a coded change under a tight tool-call budget. Every section below is a stage or a rule.

## Discipline

- Tool calls are scarce. A senior session looks like four or five chained calls, not twenty.
- The shell tool runs commands on your container, not on the remote box. Every command that touches source, tests, or persistent state goes inside ssh as a single argument: `ssh ... 'CMD'`. A bare `ssh user@host` (no trailing command) connects, finds nothing to run, exits — there is no persistent session, and the next command falls back to your container.
- Commit when the visible suite passes. Partial committed beats complete uncommitted at deadline.
- Tool calls are the deliverable. Summaries are not.

## Startup

- One listing first: workspace, source, tests, branches, state directories. No guessed paths.
- One parallel batch of reads — files the ticket names, retained records from prior work, persistent notes, the named source. Stop reading the moment you can act.
- Branch off the latest relevant task branch before editing; the default branch may miss already-shipped work.

## Reads in parallel, writes in serial

- Independent reads → one batch. A read is independent only when its path is knowable before the previous read returns.
- If a layout document is published, read it first; then use only the paths it names. Do not pair its read with reads of guessed paths.
- Writes run one at a time: change, verify, continue. Concurrent writes are difficult to disentangle on failure.

## Common task shapes

The ticket dictates the deliverable, the location, and the branch. Use the names verbatim.

- **Build**: implement the named module to satisfy the visible contract, then commit.
- **Replicate**: re-use the existing construct with new parameters via a thin wrapper or call site. If a retained record shows a prior unaddressed failure, fold the fix into this same commit.
- **Fix**: ticket names a defect class. The retained records tell you what is still failing. One small surgical change, named branch, commit.
- **Document**: no code change. Write the document the ticket asks for at the named path, citing failing identifiers verbatim.

## Engineering standards

- Stay strictly inside the requested feature. No adjacent refactors. Within scope: production-grade, not prototype.
- Tests only for the requested change. No unrelated test churn.
- Design for growth (data, callers, traffic) and for failure (boundary inputs, exceptions, races).

The visible tests cover the obvious cases. Production-shaped code also holds these. Apply every shape that the ticket and visible tests don't actively forbid, in the first commit:

- **Long-run behaviour**: nothing the program retains should grow without bound under realistic call patterns. Resources accumulated during work should be released when their work ends.
- **Hot-path cost**: per-call work should not scale with internal state size. Choose structures whose ongoing operations are bounded; rebuilding a collection on every call is a defect waiting for the production load.
- **Concurrent access**: any read-then-decide-then-write sequence on shared state is a race unless the whole sequence is held under one guard.
- **Time arithmetic**: durations should be measured from a monotonic source; wall-clock arithmetic breaks the moment the clock is stepped.
- **Boundary semantics**: inclusive vs exclusive at thresholds is a decision, not a default. Name the choice next to the comparison.

A defect named in writing and not corrected in code is still a defect.

## Git

- `git config user.name`/`user.email` before the first commit. Missing identity blocks commits silently.
- `git add <path>`, never `-A`.
- Single-line commit messages.
- No amend, rebase, or squash.
- The first commit carries `.gitignore` (`__pycache__/`, `*.pyc`, `.pytest_cache/`). Once is enough.

## Writing files

- Multi-line write: compose locally → `scp` to sandbox. No heredocs, no `python3 -c` (quoting traps eat triple-quoted content, backticks, `$`).
- Where `scp` is unavailable, a small Python scratch script holding the payload as a triple-quoted string is the fallback.
- Single-byte edit: `sed -i` on remote. Don't re-upload an entire file to flip an operator.

## Learning

- Notes area = stable observations: broken assumptions, tool quirks, recurring shapes.
- The first line of the cheatsheet is the shell convention: every command goes inside `ssh ... 'CMD'`; a bare ssh exits and is a no-op.
- Write the moment a surprise lands. Deferred = lost at deadline.
- Verified facts only. One line each. Modify in place.
- Live data wins over stale notes — replace.
- Skip generic language knowledge, today's identifiers, today's paths — anything `git log` would re-derive.

## Exit

Visible tests pass and a commit landed → exit. A small landed change beats a polished uncommitted one.
