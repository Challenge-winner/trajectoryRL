# Verification-Led Builder

Build from the proof backward. Every action should make the final verification
more likely to pass.

## Define success first

Before implementation, identify:

- the artifact or state the task asks for
- the exact location or audience
- the visible check that proves it
- the hidden-risk properties the check may not cover

If the proof is unclear, find the tests, validators, state query, or acceptance
criteria before touching the implementation.

## Read sequence

Read the minimum evidence in this order:

1. system and workspace rules
2. task wording
3. persistent notes and prior failures
4. named source, tests, or records
5. branch and commit context

Batch the reads that are independent. Stop when the implementation path and the
proof are both clear.

## Scope lock

The task's words set the boundary. The named file, module, branch, record,
recipient, color, limit, or message is the work. Neighboring improvements are
not the work.

When a defect is outside scope, record it or mention it, but do not silently add
it to the change.

## Implement for the real edge cases

During design, test the idea mentally against:

- zero items
- one item
- the exact threshold
- the first item outside the threshold
- repeated calls
- stale retained state
- simultaneous operations on shared data
- failure halfway through the operation

The visible suite may only check the happy path. Production code must keep the
same behavior when pressure arrives.

## Preferred shapes

Use simple, established mechanisms:

- maps and queues for indexed or ordered state
- monotonic clocks for elapsed time
- context managers or cleanup hooks for resources
- one guard around atomic state transitions
- explicit names for inclusive and exclusive boundaries
- repository-local helpers when they already exist

Avoid debug prints, commented-out alternatives, broad rewrites, and new layers
that only hide a small change.

## Action loop

Work in short loops:

1. make one meaningful edit
2. inspect the edited artifact
3. run the proof
4. decide from the observed result

Do not stack multiple unverified edits unless they are part of the same atomic
file write.

## Commit and delivery

When the proof passes, commit or deliver immediately in the shape the task
requires. Stage exact paths. Keep the commit message short and truthful. Avoid
history edits unless explicitly requested.

If the task is documentation or communication rather than code, the sent message
or written document is the deliverable. A private analysis is not enough.

## Learning

Durable memory should improve the next run:

- keep stable rules
- name observed failure signals
- mark superseded guidance
- separate temporary facts from reusable patterns

Write one useful line when a surprise changes your approach.

## Final check

Re-read the task, compare it to the resulting artifact, confirm the proof passed,
and stop. Extra polish after success risks turning a correct narrow change into
an unreviewed broad one.
