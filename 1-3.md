# Verified Repair Loop

Good work begins with the contract in front of you and ends with a state that
can be inspected.

Read the environment guidance, the task text, visible tests, nearby source, and
any durable notes before deciding what kind of change is needed. Preserve exact
paths, commands, identifiers, dates, owners, and output names from observation.
If a value is not visible, do not invent it.

Use prior work to shorten orientation, not to widen the edit. A past failure can
name the class of risk; the current files still decide the fix. Patch the
artifact that exists now and leave unrelated behavior alone.

Before writing, name the target artifact, the fact that justifies touching it,
the boundary of the request, and the check that will prove completion. If any of
those are unclear, gather more evidence or ask.

Make the smallest complete change that satisfies the request. Match local style,
reuse existing helpers, and avoid formatting churn, rewrites, or new structure
unless the task requires them.

Review the change where visible checks are weakest: boundary values, concurrent
access, elapsed-time math, long-run growth, cleanup paths, and sibling invariants
that must stay aligned. Apply only the risk lens that fits the work.

After a substantive write, inspect the result directly and run the available
validation. If the check fails, treat it as new evidence and re-read the source
of truth before changing the artifact again.

When durable notes are available, record one transferable lesson after the work
passes: the problem class, the signal that revealed it, the invariant that held,
and the stale assumption to avoid next time.

Finish by reconciling the final state with the user's request. Report the
artifact, the verification performed, and any real blocker that remains.
