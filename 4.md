# Engineering Operating Protocol

*Operating protocol for a programming task. Every section below is a stage or rule — follow them while you work.*

## Discipline
- Commit the moment the deliverable is ready. A committed partial survives a timeout; complete work that never gets committed disappears with the clock — recovery is impossible from an uncommitted state.
- Act, don't describe. A prose summary of what you did is not a commit; only a commit is a commit.

## Startup
- Begin with one listing of the layout — workspace root, project structure (source, tests, branches), and any state/results/notes directories. Skip files the harness already loaded. Reading by guessed path wastes turns when the guess is wrong.
- Once the layout is known, batch the targeted reads in parallel: the files the task names, plus any state, result, or note files the listing revealed. Stop reading once you can act — additional reads delay the actual work.
- Before any edit, branch off the latest relevant branch — the one already carrying the work this task extends. Defaulting to the integration branch re-introduces work already shipped.

## Batching Independent Reads
- Group independent reads into a single batch whenever the environment allows it. Sequential reads cost a turn each — when paths are already known, that's wasted budget.
- Two reads are independent only when the second path does not depend on the first output. If the first read tells you where the second one lives, you cannot batch them.
- If one file names the real paths to use, read that file first, then use its paths in the next step.
- Writes stay serial: make one change, verify it, then continue. Verification before the next change catches regressions early.

## Engineering Standards
- Stay within the requested feature — no refactors, renames, "while we're here" cleanups, or bug fixes outside the task's scope. If you spot a bug outside scope, report it rather than silently fix it; surfacing concerns is professional, silent scope expansion is not. Within the requested feature, ship a production-ready implementation, not a prototype. The scope boundary is at the feature level; the quality bar within the feature is full production readiness.
- Add new files only when the task asks for them. Adjacent artifacts (tests, configs, helpers) stay as they are by default — adding them is scope creep that hurts change-minimality.
- Design every feature for growth (more data, users, traffic) and for failure (edge cases, exceptions, boundary conditions). The textbook minimum rarely survives realistic load — what passes today's tests often breaks under tomorrow's traffic.

## Git
- Before the first commit, set `git config user.name` and `user.email` — commits fail silently without an identity, leaving the work uncommitted.
- Stage specific paths (`git add src/file.py`); `git add -A` is broader than usually intended and pulls in caches and editor backups.
- Single-line commit messages.
- Do not amend, rebase, or squash. History rewrites lose the audit trail.

## Writing files
- For multi-line writes, compose the file locally and `scp` it to the sandbox. scp copies bytes exactly, so triple-quoted strings, backticks, and `$` survive intact. Heredoc and `python3 -c` patterns mangle these characters silently — debugging the corruption costs more than just using scp from the start.
- If scp truly isn't available, fall back to a `python3` scratch script with the content in a triple-quoted string. Otherwise, scp.
- For one-line edits (flipping an operator, swapping a constant), use `sed -i` or equivalent in-place replacement on the remote. Re-uploading the whole file to change a single character widens the diff for no reason.

## Learning
- Use the workspace's notes area for stable observations — broken assumptions, tooling quirks, recurring patterns. Future sessions read these to recognise patterns; record what generalises.
- Add a note the moment a surprise lands. Deferring to the end means the note is lost when the timeout fires.
- Write only what you've verified. Unverified guesses pollute the channel — later readers take them as fact.
- One line per observation. Modify in place; don't duplicate.
- When live data contradicts a stored note, live data wins: replace the stale entry rather than leaving both.
- Skip generic programming knowledge, today's IDs or paths, anything derivable from `git log` — the notes are for what doesn't fit elsewhere.
